# 性能优化与等价性验收

日期：2026-11-13。目标是在既有任务、特征公式、分折和模型结构不变的前提下减少计算和数据装箱开销。所有对比使用同一份官方修正版 ASSISTments2009，原始文件 SHA-256 见 `data/assist2009_source.json`。

## 1. 实施内容

### C++17

- 题目和概念计数使用连续 `std::vector<Counter>` 存储训练集正数紧凑 ID；负数及稀疏超大正数 ID 保留哈希回退。数组上界受到交互条数约束，避免收到 `INT32_MAX` 一类键时分配巨型数组。
- `TransformSequence<false>` 用于完整训练先验的普通提取，编译期去掉排除折查找和差分；`TransformSequence<true>` 保留 OOF 差分。
- 工作线程按连续学生区间写入输出，各区间互不重叠。不同学生长度不同时仍可能存在负载差异，因此不承诺每个数据规模都等比例受益。
- 同一序列的学生折归属检查由逐交互改为逐序列；输入校验仍确保序列内只有同一学生。

### Python 数据流程

- CSV 只读取算法实际使用的列。
- 清洗后保存列数组，不再为每次真实作答构造 `RawInteraction` 对象；使用 NumPy/Pandas 向量化 ID 映射，直接构造 `ROW_DTYPE` 交互数组，不再逐条创建 `Interaction` 对象。
- 同一个学生的分块是连续数组视图。`pack_sequences` 在确认多个视图完整连续覆盖同一底层数组后直接复用该数组；非连续输入仍进行一次拼接。旧的对象输入路径保留用于小型测试及参考调用。
- 词表仍仅由 Train 建立；未见概念保持互相独立的负 ID。数据清洗顺序、学生划分、OOF 折、原始步号和标签均保持不变。

### PyTorch

- 评估时仅向设备传输该批最大有效长度，元数据留在 CPU；训练仍保持原来的样本顺序与张量形状。
- 不采用按长度重排训练 Batch，也没有启用混合精度。前者改变优化顺序，后者改变舍入精度；动态裁剪训练张量还会改变 Dropout 随机数分配。它们可以是后续单独研究的训练设置，但不能称为“结果 100% 不变”的优化。
- 真实实验配置使用 `device: auto`；显式请求不可用 CUDA 时给出明确错误。本机已安装 PyTorch `2.14.1+cu130` 并识别 RTX 3050 Ti Laptop GPU（4GB）。
- CUDA 验收发现注意力反向传播在 `warn_only=True` 时可选择非确定性实现，正式实验统一改用严格确定性算法和 `CUBLAS_WORKSPACE_CONFIG=:4096:8`。这是正式实验开始前固定的运行约定，旧 CPU 冒烟记录保留其原环境信息。

## 2. 等价性证据

`outputs/performance-before/reference.npz` 与 `outputs/performance-after/reference.npz` 逐项对齐：

- 训练交互结构化数组、序列 offsets、OOF fold_ids：逐元素完全一致。
- Train / Val / Test 全部十维特征：float32 逐元素完全一致。
- 三个集合内全部 Dataset 样本（题目、知识点、标签、特征、mask、真实/局部步号、题频等）的 SHA-256：完全一致。
- 稀疏超大正数 ID、负数 ID、空输入、1/4 线程、不同时间/耗时元数据：测试通过。
- 六模型分别在 CPU/CUDA 上验证评估裁剪前后的有效位置 logits，误差不超过 `1e-6`。这里只主张数值容差内一致，不主张不同矩阵形状下浮点结果逐位一致。
- 总计 **63 项 pytest 测试通过**，包含断点恢复训练与已完成 Test 缓存复用；C++ 原生测试也通过，编译零警告。

## 3. Python 数据准备耗时和内存

原实现和优化实现在同一进程中交替测量三次，以降低运行顺序偏差。计时包含 CSV 读取、清洗、学生划分、OOF 特征构建和首次构造 Dataset 张量；下表为总耗时中位数。

| 指标 | 优化前 | 优化后 | 解释 |
| --- | ---: | ---: | --- |
| 数据准备总耗时 | 6.209 s | 2.910 s | 约 2.13 倍提速 |
| Python 跟踪分配峰值 | 758.30 MiB | 187.12 MiB | 约减少 75.3% |
| 准备后 Python 跟踪分配量 | 100.65 MiB | 38.33 MiB | 减少交互对象及未使用字段 |

内存指标由 `tracemalloc` 在独立测量阶段获得，在数据读取与特征准备结束时读取峰值，未遍历构造全部 Dataset 样本张量。它不是操作系统 RSS、整机内存或显存峰值，不能解释为总进程内存的严格上界。原始数据见 `outputs/performance-comparison/pipeline_times.json` 和 `pipeline_memory.json`。

## 5. 动态长度裁剪的实际边界

在构造的短序列评估批次中（32 个学生、最大有效长度 35、HSF_Gate、隐藏维度 64）：

| GPU 前向评估 | 固定 200 步 | 裁剪到 35 步 |
| --- | ---: | ---: |
| 50 次测量的中位耗时 | 5.887 ms | 2.510 ms |
| 额外显存分配峰值 | 74.48 MiB | 3.60 MiB |

这说明短批次评估确实受益，但不是整个真实训练的速度提升。对当前固定划分和种子 42 的实际 Batch 统计发现：

- 训练：种子 42 第一轮顺序中的 94/94 个 Batch 都含 200 步满块，裁剪后长度完全不变；这不是对所有种子、所有轮次的穷举证明。
- 验证：14 个 Batch 中 12 个已经满长，注意力矩阵元素数量预计仅减少约 5.7%。
- 测试：27 个 Batch 中 21 个已经满长，注意力矩阵元素数量预计减少约 8.1%。

因此不能根据单个 35 步批次宣称本任务的训练获得十几倍加速，也不能把理论 `L²` 比值等同于完整模型运行时间。当前实现采用评估裁剪，保留正式训练协议。
